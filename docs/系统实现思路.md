# PRMS 系统实现思路

## 1. 当前定位

这个仓库的目标不是只放一个番茄识别 Demo，而是把论文中的完整系统拆成可复现、可逐步验证的工程项目：

- 导航与定位：参考 NEXTE_Sentry_Nav 的 FAST-LIO、重定位、move_base、速度平滑和串口通讯方法。
- 路径组织：在局部导航之上增加拓扑地图，负责温室垄道级全局路径引导。
- 成熟度识别：接入已有 PRMS 识别仓库，完成全景图投影、左右视图提取、目标检测和成熟度分类。
- 时空融合：把检测结果和机器人位姿按时间戳对齐，投影到温室空间坐标。
- 结果展示：输出三维成熟度分布图、统计表和可交互页面。

我现在采用的是“先接口、再算法、再实测数据”的路线。原因是论文开源复现最怕一开始就堆完整硬件依赖，别人没有机器人、LiDAR 或温室地图时会完全跑不起来。先把 ROS 包、消息、话题、仿真验证搭稳，后面再逐层加入真实导航和识别证据。

## 2. 已完成内容

### 2.1 系统级 ROS 框架

仓库已经包含 6 个 ROS 包：

- `prms_msgs`：定义成熟度观测消息。
- `prms_topology`：发布温室拓扑路径。
- `prms_perception_bridge`：把 PRMS 检测结果桥接为 ROS 消息。
- `prms_fusion`：预留位姿、TF、检测结果的融合节点。
- `prms_sim`：提供轻量仿真定位和自动验证节点。
- `prms_bringup`：集中管理 launch、config 和示例地图。

### 2.2 导航依赖准备

本地已经浅克隆 NEXTE_Sentry_Nav：

```text
third_party/NEXTE_Sentry_Nav_src
```

识别到的关键包包括：

- `sentry_slam/FAST_LIO`
- `sentry_slam/FAST_LIO_LOCALIZATION`
- `sentry_nav`
- `sentry_comm/sentry_serial`
- `sentry_tools/velocity_smoother_ema`

目前这些代码作为外部依赖保留在 `third_party/`，不直接进入主仓库历史。这样主仓库更干净，也避免混入第三方代码版权和体积问题。

### 2.3 可复现 smoke 验证

当前有两层轻量验证。

第一层：拓扑路径 + 模拟定位。

```powershell
powershell -ExecutionPolicy Bypass -File scripts\run_wsl_smoke.ps1
```

验证内容：

- catkin 能编译 6 个 ROS 包；
- 能发布 `/prms/topology/global_path`；
- 能发布模拟 `map -> body` TF 和 `Odometry`；
- 模拟机器人能沿拓扑路径前进。

第二层：参考栅格地图 + 拓扑路径 + 模拟定位。

```powershell
powershell -ExecutionPolicy Bypass -File scripts\run_wsl_map_smoke.ps1
```

验证内容：

- `map_server` 能加载参考栅格地图；
- `/map`、拓扑路径、模拟里程计同时可用；
- 验证节点能自动判断系统链路是否连通。

实测通过结果：

```text
PRMS simulation smoke passed: path_poses=3 odom_samples=8 travelled_m=0.560
PRMS map smoke passed: map=680x130 resolution=0.050 path_poses=3 travelled_m=0.560
```

第三层：闭环导航 smoke。

```powershell
powershell -ExecutionPolicy Bypass -File scripts\run_wsl_closed_loop_nav_smoke.ps1
```

验证内容：

- 拓扑路径发布节点输出路线；
- 简易路径跟踪器根据路线和里程计发布 `/cmd_vel`；
- 底盘仿真节点根据 `/cmd_vel` 积分生成 `Odometry` 和 TF；
- 验证节点检查机器人是否到达最终 waypoint。

这一层是当前仓库推荐保留的导航验证：它证明导航接口和闭环控制链路能工作，但不把它包装成真实温室 `move_base` 性能。

当前实测通过结果：

```text
PRMS closed-loop navigation smoke passed: path_poses=3 cmd_samples=88 final_error_m=0.195
```

## 3. 为什么先做轻量仿真

我的建议是先保留这条轻量仿真路线，不急着直接上完整 Gazebo 或真实机器人。

原因有三点：

1. 对审稿人和读者更友好。没有机器人和 LiDAR 的人，也能验证代码结构、消息接口和基本数据流。
2. 对工程开发更稳。拓扑路径、定位、识别、融合都能单独验证，出了问题容易定位。
3. 对论文复现更诚实。轻量仿真只证明接口链路，不夸大成真实温室导航性能；真实性能必须用实测地图、rosbag 和标注数据支撑。

完整 Gazebo 仿真可以作为下一层，但它应该建立在当前 smoke 测试已经稳定的基础上。

## 4. 下一步开发路线

### 阶段 A：二维地图导航仿真

目标：在参考栅格地图上跑 `map_server + move_base + 拓扑 waypoint`。

需要完成：

- 把拓扑路径转换成顺序 `move_base` goal。
- 增加一个轻量底盘仿真节点，订阅 `/cmd_vel`，发布 `/Odometry`。
- 用 `move_base` 在参考地图中完成从入口到出口的路径跟踪。
- 输出路径长度、耗时、是否到达终点。

这一阶段可以初步验证导航框架，但仍不能代表真实温室性能。

### 阶段 B：接入 NEXTE 导航栈

目标：把 NEXTE 的 `sentry_nav`、速度平滑、串口桥接和 FAST-LIO 接到 PRMS 系统。

需要完成：

- 整理 NEXTE 依赖安装脚本。
- 固定 FAST-LIO、Livox 驱动、PCL、Sophus 等版本。
- 写统一 bringup launch。
- 明确 `prior_map`、`Odometry`、`body`、`body_2d`、`map` 等 topic/frame 映射。

### 阶段 C：接入 PRMS 识别仓库

目标：让识别仓库不只是离线生成 HTML，而是能把检测结果发布到 ROS。

需要完成：

- 把 PRMS 输出转换成 `/prms/perception/detections`。
- 支持离线 CSV replay 和在线图像推理两种模式。
- 固定检测模型、阈值、亮度增强策略和输出格式。

### 阶段 D：时空融合与三维地图

目标：把成熟度检测结果和位姿对齐，形成三维成熟度分布。

需要完成：

- 统一图像、LiDAR 位姿、深度/距离证据的时间戳。
- 用 TF 外参把相机观测投影到 `map` 坐标系。
- 区分左侧作物行与右侧作物行，避免一个点覆盖两面。
- 输出可交互三维成熟度地图和 CSV/JSON 数据。

### 阶段 E：论文级复现材料

目标：让开源仓库能支撑论文关键结论。

需要完成：

- 提供最小数据集。
- 提供一键复现实验脚本。
- 提供检测、导航、定位、融合的量化评估结果。
- 明确哪些结果来自真实实验，哪些只是演示或仿真。

## 5. 还需要你提供的数据

如果要继续从“框架可运行”推进到“论文可支撑”，最有价值的数据是：

- 真实温室栅格地图：`.pgm + .yaml`。
- FAST-LIO 点云地图或建图结果。
- 一段真实 rosbag：至少包含 LiDAR/odom/TF，最好包含 `/cmd_vel`。
- 全景图原始序列及时间戳。
- 机器人位姿 CSV 或 TF 导出的轨迹。
- LiDAR、底盘、全景相机、深度相机之间的外参。
- 少量人工标注真值：番茄框、成熟度类别、植株位置或番茄三维位置。

## 6. 对外开源时的表述边界

当前仓库可以说：

- 提供了 PRMS 系统的 ROS 工程框架。
- 提供了拓扑路径、模拟定位和参考地图的可复现 smoke 测试。
- 提供了导航、识别、融合三部分的接口定义和接入路线。

当前仓库暂时不应说：

- 已经完整复现真实温室自主导航性能。
- 已经证明真实三维番茄定位精度。
- 已经完成跨日期、跨视角的单果长期跟踪。

这些结论需要实测数据和量化评估支撑。仓库现在做得比较稳的是“系统骨架和可复现入口”，下一步再逐层把真实证据补上。
